# Changes from the original The_Gate plugin

This document explains what was changed in this fork, and why, for anyone comparing it against
the original plugin by EndMy5uffering.

The short version: this started as a version-compatibility update (Minecraft 1.21.1 → 26.2) and
ended up requiring a full rewrite of one specific subsystem, plus a handful of unrelated bug fixes
found along the way. No gameplay features, commands, permissions, or config format were
intentionally changed — the goal throughout was "make it work on 26.2, unchanged otherwise."

This fork ships as **two build variants**, Paper and Spigot, since they ended up needing
meaningfully different handling for one dependency (see "The Spigot variant" below). The repo is
laid out as `common/` (shared source, both variants) + `paper/` and `spigot/` (the small number of
files that differ per platform).

## Why an update was needed at all

Minecraft moved to year-based versioning in 2026 (1.21.x → 26.x). The plugin was built against
1.21.1 specifically, and its `plugin.yml` capped compatibility there. Getting it running on 26.2
required more than a version bump, for reasons below.

## The core rewrite: client-side rendering

The plugin builds every gate's visuals (ring, chevrons, symbols, DHD, iris) out of fake armor
stands, shown only to nearby players via direct network packets. The original implementation did
this by extending raw internal Minecraft classes directly (`net.minecraft.world.entity.decoration.EntityArmorStand`)
and calling obfuscated methods tied to one specific build of CraftBukkit (`v1_21_R1`).

That obfuscation is regenerated by Mojang on every Minecraft version. This wasn't a
small-fix situation — the original packet code could not run on 26.2 at all without a rewrite.

**What replaced it**, in `com/packageing/tools/packagetools/` (in `common/`, shared by both
variants):
- **[PacketEvents](https://github.com/retrooper/packetevents)** (2.13.0) — public, version-abstracted packet sending, maintained by a team that tracks Minecraft's protocol changes as their job. As of 2.13.0 it explicitly supports 26.2.
- **[EntityLib](https://github.com/Tofaa2/EntityLib)** (3.3.6, built on PacketEvents) — typed entity metadata (pose, rotation, visibility), so version-specific byte offsets don't need to be hand-tracked either.

Every public method on `ArmorStand`/`PackageManager` kept its original name and signature, so
nothing in `thegate.*` (GatePackages, GateChevron, IrisPart, CreateGate, the animation classes,
TheGateMain) needed logic changes — only the internals of those two classes changed.

**Build changes that follow from this (Paper variant):**
- `pom.xml` adds `paper-api` (26.2), `packetevents-spigot`, and `io.github.tofaa2:spigot`
  (EntityLib) as dependencies, shaded and relocated (`thegate.libs.*`) so they don't collide with
  other plugins on the same server that also shade these libraries.
- `TheGateMain` gained an `onLoad()` step to bootstrap PacketEvents (must run before any player
  connects) and initializes EntityLib in `onEnable()`.
- `plugin.yml` `api-version` bumped to `26.2`.

The Spigot variant handles PacketEvents differently — see below.

## The Spigot variant

Both variants share the same `common/` source and the same architecture (PacketEvents +
EntityLib). Getting this working correctly on genuine Spigot (as opposed to Paper) surfaced four
separate problems, three of them in EntityLib's own code rather than anything in this fork.

### Why PacketEvents isn't bundled in the Spigot build

The Paper build shades (bundles) PacketEvents directly into the plugin jar. Attempting the same on
Spigot hit a real, hard conflict: Paper 26.2 needs to compile against Adventure 5.x (a newer
Minecraft/Paper API surface requirement), but packetevents-spigot:2.13.0's own compiled
`BukkitLogManager` class references `net.kyori.adventure.util.Buildable$Builder`, a type that does
not exist in Adventure 5.x at all - only in the older 4.x line. No single Adventure version
satisfies both requirements at once when everything is bundled into one jar.

**Resolution:** the Spigot variant does not shade PacketEvents. Instead, `pom.xml` marks it
`provided` scope, and `plugin.yml` declares `depend: [packetevents]` - server owners install
[PacketEvents](https://www.spigotmc.org/resources/packetevents.80279/) as its own separate plugin,
same as many other Spigot plugins that depend on it. This is also PacketEvents' own documented
preferred usage pattern (shading is explicitly the advanced/opt-in path in their docs). Once
PacketEvents runs standalone, its internals live in their own classloader with their own correctly
matched Adventure version, completely isolated from this plugin's own bundled Adventure copy - so
the conflict disappears entirely rather than needing a workaround.

Following from this, `TheGateMain.onLoad()`/`onEnable()`/`onDisable()` no longer call
`PacketEvents.setAPI()`/`.load()`/`.init()`/`.terminate()` in the Spigot variant - a standalone
PacketEvents plugin creates and manages its own instance automatically, per PacketEvents' own
documentation for non-bundled usage.

### Three EntityLib bugs specific to non-Paper Spigot

EntityLib's own Spigot-platform code (`me.tofaa.entitylib.spigot.SpigotEntityIdProvider`) has
several assumptions that don't hold on modern, genuine Spigot (as opposed to Paper, which the
library appears to be primarily tested against). All three only affect the non-Paper code path.
This fork works around them by substituting a corrected replacement class
(`spigot/src/main/java/me/tofaa/entitylib/spigot/SpigotEntityIdProvider.java`) into the shaded jar
in place of EntityLib's own, via a `<filter><excludes>` entry in `pom.xml`. These are genuine
upstream bugs, not something specific to this fork's setup - worth reporting to EntityLib's
maintainer regardless of this fork's fate.

1. **Package-name parsing crash.** `getEntityClass()` eagerly computes
   `Bukkit.getServer().getClass().getPackage().getName().split("\\.")[3]` even when the result is
   never used (only needed on pre-1.17 servers). Modern CraftBukkit's package name (both Paper and
   genuine Spigot, since Mojang mappings became standard) is `org.bukkit.craftbukkit` - three
   segments, not four - so this throws `ArrayIndexOutOfBoundsException` unconditionally on any
   modern server. Fixed by only computing that value inside the branch that actually needs it.

2. **Compile-time dependency on a removed method.** The Paper-specific branch of
   `detectIdSupplier()` uses a direct method reference to a zero-argument
   `UnsafeValues#nextEntityId()` overload for pre-26.2 Paper servers. Current `paper-api` builds
   have removed that overload entirely (only the newer `nextEntityId(World)` remains), so the
   direct method reference fails to *compile* even though that branch never executes at runtime
   for 26.2+. Fixed by using reflection (`Method` lookup) instead of a direct method reference,
   deferring the "does this exist" check to runtime, where the branch is never reached.

3. **Wrong field found, and it's `static final`.** The non-Paper fallback (`resolveAtomicSupplier`
   / `resolveLegacySupplier`) reflectively guesses at Minecraft's internal entity-ID counter field
   by trying candidate names (`"entityCount"`, `"d"`, `"c"`, `"b"`, etc.). On Minecraft 26.2's
   `Entity` class, this guessing finds an unrelated field that happens to share a candidate name
   (`CURRENT_LEVEL`) - and that field is `static final`, which modern Java flatly refuses to let
   reflection modify at all, throwing `IllegalAccessException`. Rather than chase the correct field
   name for 26.2 (which would only need chasing again on some future version), this fork replaces
   the whole non-Paper fallback with a simple self-managed counter starting from a high number
   (1,500,000,000) that won't collide with real entity IDs. This needs no knowledge of Minecraft's
   internal field names at all, and is more robust against future Minecraft versions than the
   reflection-guessing approach it replaces.

### Other Spigot-variant notes

- Adventure API is bundled at version `5.2.0` (matching Paper's own version) in the Spigot variant
  too, now that PacketEvents itself is no longer shaded - the version conflict described above no
  longer applies once PacketEvents runs standalone.
- This variant still compiles against `paper-api` rather than genuine `spigot-api`. Since Paper API
  is a strict superset of Spigot's, this compiles fine either way, but means there's a small
  residual chance of an undiscovered Paper-only method call somewhere in the decompiled codebase -
  the same category of issue as the Adventure dependency above, just not yet surfaced. This would
  show up as a `NoSuchMethodError` at runtime on genuine Spigot, not a compile error.

## Decompiler artifacts (not logic changes)

The original `.class` files had to be decompiled to editable source to work with at all (no
source was available). The decompiler (CFR) occasionally produced invalid or subtly wrong Java
from valid bytecode — mostly mangled `try`-with-resources reconstructions, a few duplicate local
variable names, and some lost generic type information (particularly for code with no external
classpath available at decompile time). These were fixed back to plain, equivalent, compiling
Java. No behavior was intentionally changed by any of these — flagging them mainly so they aren't
mistaken for functional changes:

- `bstats/Metrics.java`, `thegate/main/save/DBGateAccess.java` — malformed try-with-resources
  reconstructions
- `thegate/animaitons/AnimationDialing.java`, `AnimationDialingSingleGate.java`,
  `thegate/guis/DHD_GUI.java` — duplicate variable names from decompiler scope handling
- `thegate/main/save/DBGateAccess.java`, `thegate/commands/TheGateCommand.java` — a bogus
  `(Object[])` cast that broke generic type inference on `Lists.newArrayList(...)` calls
- `thegate/gate/CreateGate.java`, `thegate/guis/AbydosGUI.java`, `thegate/guis/QuickDialGUI.java` —
  raw (non-generic) `List`/`Set` declarations that caused lambda parameters to erase to `Object`
- `thegate/guis/CoOwnerListGUI.java` — a variable declared as the general `ItemMeta` interface
  where a `SkullMeta`-only method was called; fixed with an explicit cast at the call site

## Bugs found and fixed along the way

Real, functional bugs found during testing — not decompiler artifacts. Documented here since
they're worth knowing about regardless of what happens with this fork.

### 1. Armor stand spawn rotation

Early in testing, every fake armor stand (ring segments, symbols, chevrons) spawned facing the
same fixed direction instead of the correct per-piece rotation, making the ring/symbols look
scattered. Root cause: in `ArmorStand.CreateArmorStand()`, the initial spawn packet was built
using the *caller's* `Location` object's yaw/pitch, which defaults to `0` in most of the call
sites in `CreateGate.java` (`new Location(world, x, y, z)` — no yaw/pitch args), rather than using
the `rotBody` parameter that's supposed to control this. Fixed by using `rotBody` directly for the
spawn yaw. This is a bug in the new packet-layer code, introduced during the rewrite above, not
present in the original 1.21.1 version.

### 2. Save-queue race condition (`DatabaseManager.java`)

**This one exists in the original plugin too, on any Minecraft version — not introduced by this
fork.** The plugin queues pending SQL writes in a plain `ArrayList<String>`, drained by a
dedicated background thread. That thread iterates the list with a `for`-each loop while other
threads (any code calling `asyncSqlStatements()` — including the manual "Save Gate List" button
and gate creation) can concurrently add to the same list, with no synchronization protecting the
list itself.

If a write happens to land while the worker thread is mid-iteration, Java throws a
`ConcurrentModificationException`. That exception is a `RuntimeException`, not a `SQLException`,
so it isn't caught by any of the surrounding `catch` blocks — it escapes the worker thread
entirely, silently killing it. Once that happens, every future save request is added to a queue
that's no longer being processed by anything, until the plugin (and thread) restarts.

**Symptom this produces:** the "Save Gate List" button (and effectively all saving) appears to
work exactly once per server session, then silently stops working until a restart — and if the
server goes down uncleanly (crash / force-kill / host panel hard restart) before that, any gates
created since the last successful save are lost, since they were only ever sitting in the dead
queue rather than written to disk.

**Fix:** replaced the plain `ArrayList<String>` queue with `java.util.concurrent.ConcurrentLinkedQueue<String>`,
and rewrote the worker loop to drain it via `poll()` instead of iterate-then-remove. This removes
the concurrent-modification hazard entirely rather than working around it, and also fixes a
secondary issue where a single permanently-failing SQL statement could previously never be
removed from the queue, causing the worker to spin on it forever instead of returning to process
new work.

### 3. Gates not appearing reliably on server startup

A newly loaded gate could fail to render for players already online when loading finished, with no
automatic recovery until the manual repair action was used. Root cause: `DBGateAccess.Load()`
reads gate data from the database on a background thread, then populated the same in-memory
structures the main thread reads for "is a gate nearby?" checks - with no synchronization, and no
re-check triggered once loading actually completed. If a player logged in and moved before the
background load finished, nearby gates were simply never displayed. Fixed by moving the actual
`GateManager.addGate()` call onto the main thread via the Bukkit scheduler, and triggering one
proximity re-check for all already-online players immediately after loading completes.

### 4. Gates going invisible after reconnecting (Paper and Spigot both)

A gate a player had already seen would sometimes not reappear after they disconnected and
reconnected, even after walking back into range - only a manual repair fixed it. Root cause:
EntityLib tracks, per fake entity, which player UUIDs have already been sent a spawn packet, to
avoid redundant network traffic. Disconnecting a player never cleared that per-entity tracking, so
on reconnect (same account UUID, new session) EntityLib believed the player had already seen the
entity and skipped sending anything. Fixed by calling the existing despawn/cleanup path
(`Vanish(p)`) on disconnect too, matching what already happened when a player simply walked out of
a gate's range.

### 5. Colored gate labels rendering as literal text

Name/address/description labels above gates (Abydos Cartouche) were showing literal `§`-style
color codes instead of actual colors. Root cause: the new `Component`-based text API needs color
codes explicitly parsed via Adventure's legacy-format deserializer; the initial implementation
used a literal-text constructor instead, which doesn't parse formatting codes at all. Fixed by
using `LegacyComponentSerializer.legacySection().deserialize(...)` instead.

## Known cosmetic issue — not from this fork

Some ring symbol glyphs don't sit perfectly centered between their nearest chevrons. This was
confirmed present in the original plugin's own official SpigotMC screenshots, and reproduces
identically regardless of which direction a gate is built facing — so it's pre-existing behavior
in the original plugin's angle math, unrelated to this migration. Left unchanged.

## What was *not* changed

- Commands, permissions, config format (`config.yml`/`lang.yml` are untouched, same keys)
- Database schema
- Any gameplay logic, GUI layout, or feature behavior beyond the bug fixes listed above
- Any file not listed above

## Dependencies added

| Library | Version | Purpose | Paper variant | Spigot variant |
|---|---|---|---|---|
| Paper API | 26.2.build (range) | Server API target | provided (compile-time only) | provided (compile-time only) |
| PacketEvents | 2.13.0 | Version-abstracted packet sending | shaded, relocated | **provided** - install separately as its own plugin |
| EntityLib | 3.3.6-SNAPSHOT | Typed entity metadata on top of PacketEvents | shaded, relocated | shaded, relocated (with the `SpigotEntityIdProvider` patch above) |

Paper users: everything is bundled - just the one jar. Spigot users: also need to install
PacketEvents as a separate plugin (see "The Spigot variant" above).
